## ⚠️ Leer antes de revertir nada

1. **Revertir el candado deja la facturación ABIERTA.** El candado es lo único que hoy impide que un
   clic en «Émettre»/«Forcer» emita una factura real e inmutable. Si lo quitas, vuelve el riesgo que
   ya se materializó una vez (ver `FACT-2026-0001`, más abajo). Antes de quitarlo, implementa la
   **Capa 2** (confirmación al emitir, `docs/pendientes.md`).
2. **El orden importa con los 3 usuarios.** Si revocas el permiso (`can_bill`) mientras esas cuentas
   siguen activas, **vuelven a ser admin a secas y pasan a ver TODA la facturación**. Bórralas (o
   bájalas a `technician`) **antes** de revertir la migración del permiso.
3. **`FACT-2026-0001` no se puede borrar.** Es la factura de prueba de 2AS (emitida por error el
   2026-06-18 y ya anulada). Las facturas son inmutables por trigger: ni `service_role` las borra.
   No intentes limpiarla; es inofensiva.
4. **El DDL en producción no va por el MCP de Supabase** (lo bloquea el clasificador). Usa el **SQL
   Editor** del dashboard, o crea una migración nueva y `supabase db push --linked`.

### Paso 2 — Revertir el permiso de facturación (`20260911130000`)

Restaura las 3 policies **exactamente** como estaban (`FOR ALL TO authenticated USING (is_admin())
WITH CHECK (is_admin())`, tal y como las crearon `20260606000000_billing_plans.sql` y
`20260606000100_invoices.sql`).

```sql
BEGIN;

DROP POLICY IF EXISTS invoices_billing_all ON public.invoices;
CREATE POLICY "invoices_admin_all" ON public.invoices
  FOR ALL TO authenticated
  USING (public.is_admin()) WITH CHECK (public.is_admin());

DROP POLICY IF EXISTS invoice_lines_billing_all ON public.invoice_lines;
CREATE POLICY "invoice_lines_admin_all" ON public.invoice_lines
  FOR ALL TO authenticated
  USING (public.is_admin()) WITH CHECK (public.is_admin());

DROP POLICY IF EXISTS billing_plans_admin_read  ON public.billing_plans;
DROP POLICY IF EXISTS billing_plans_billing_write ON public.billing_plans;
CREATE POLICY "billing_plans_admin_all" ON public.billing_plans
  FOR ALL TO authenticated
  USING (public.is_admin()) WITH CHECK (public.is_admin());

DROP FUNCTION IF EXISTS public.can_bill();
ALTER TABLE public.profiles DROP COLUMN IF EXISTS can_bill;

DELETE FROM supabase_migrations.schema_migrations WHERE version = '20260911130000';

COMMIT;
```

### Paso 4 — Revertir el código

Son merge commits, así que hace falta `-m 1` (revertir contra el primer padre, `main`). En orden
inverso al despliegue:

```bash
git checkout main && git pull
git checkout -b revert/despliegue-2026-09-11
git revert -m 1 56b64f4   # permiso de facturación (#123)
git revert -m 1 6aaa8bb   # candado de facturación (#122)
git push -u origin revert/despliegue-2026-09-11
gh pr create --fill
```

`main` está protegida con el check obligatorio `typecheck · test · build`, así que **no se puede
empujar directo**: hay que pasar por PR. Al revertir se van también sus migraciones del árbol, sus
tests (`billing-lock.test.ts`, `billing-permission.test.ts`) y el `globalSetup` de RLS.

Borra además el fichero de migración del árbol si `git revert` lo dejara (no debería):
`supabase/migrations/20260904120000_billing_lock.sql`, `supabase/migrations/20260911130000_billing_permission.sql`.

## Reversiones PARCIALES (lo más probable)

### Quitar solo el permiso, conservando el candado

Pasos 1 y 2, y del paso 4 solo `git revert -m 1 56b64f4`. El candado sigue protegiendo.

### Quitar solo a un usuario el acceso, sin tocar nada más

```sql
UPDATE public.profiles SET role = 'technician' WHERE id = '<uuid>';   -- fuera del área admin
DELETE FROM auth.users WHERE email = '<email>';                        -- o borrarlo del todo
```

### Dar facturación a un admin del SAV (lo contrario de revertir)

```sql
UPDATE public.profiles SET can_bill = true WHERE id = '<uuid>';
```

### Encender la facturación cuando el SAV se valide

Implementa **antes** la Capa 2 (`docs/pendientes.md`), y luego:

```sql
UPDATE public.billing_settings SET billing_enabled = true, updated_at = now() WHERE id;
```
