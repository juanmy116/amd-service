# Cómo deshacer F2 (2026-10-09)

> Runbook de reversión del arreglo F2 del escaneo de seguridad: el técnico no puede cambiar las
> columnas de las que sale su propio alcance RLS. Escrito el día del despliegue.

## Qué se desplegó

| Qué | Migración |
|---|---|
| Función `public.guard_tech_scope_columns()` y el trigger `trg_guard_tech_scope_columns` (`BEFORE UPDATE`) en `incidents` y en `maintenance_visits` | `20261009100000_guard_tech_scope_columns.sql` |

No toca datos: solo rechaza, para las sesiones de técnicos y clientes, los `UPDATE` que cambian
`contract_machine_id` o `assigned_to` (las dos tablas) y `machine_id`, `opened_by` o `source`
(solo `incidents`). La oficina, `service_role` y las sesiones directas a la BD no se ven afectadas.

## Síntoma que haría falta deshacerlo

Un técnico recibe «Seul le bureau peut changer la machine ou l'affectation.» al guardar algo que
antes podía guardar. No debería pasar: la app nunca cambia esas columnas con su sesión.

## Reversión

En el **SQL Editor** del dashboard de Supabase (el DDL en producción no va por el MCP), o con una
migración nueva y `supabase db push --linked`:

```sql
DROP TRIGGER IF EXISTS trg_guard_tech_scope_columns ON public.incidents;
DROP TRIGGER IF EXISTS trg_guard_tech_scope_columns ON public.maintenance_visits;
DROP FUNCTION IF EXISTS public.guard_tech_scope_columns();
```

Comprobación (debe devolver 0 filas):

```sql
SELECT tgname FROM pg_trigger WHERE tgname = 'trg_guard_tech_scope_columns';
```

Si se revierte a mano, la migración `20261009100000` sigue en el historial de `supabase_migrations`:
para que git y la BD no se desalineen, añadir después una migración que haga el mismo `DROP`.
